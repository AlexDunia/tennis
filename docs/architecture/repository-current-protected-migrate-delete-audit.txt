OLD PLAYER SYSTEM MIGRATION MAP
-------------------------------

A. Remaining dependencies on the global ApiService demo player array

- Direct: PlayerService GET /players -> player store -> global players/currentPlayer/sortedLadder/opponent lookup/role overlay and APP_CURRENT_PLAYER fallback.
- Shell: DefaultLayout autoloads the store and displays current-player identity/rank.
- Direct screen loaders: DashboardView; LadderView; ChallengesQueueView; CompeteChallengeCreateView; ChallengeDetailsView; CreateChallengeView; PlayHubView; PlayView; MatchDetailsView; FriendlyMatchFlowView; ProfileView; LadderPlayerAccessView; ChairUmpireInvitationView; LiveOperationsView; LiveOperationDetailView; TournamentCreate; TournamentOverview; TournamentCategory; TournamentGallery; and legacy-but-test-retained ChallengesView.
- Indirect consumers: LiveMatchView, LiveScoreboardView, TournamentSchedule, DefaultLayout, LadderMatchManageDialog, match/challenge stores, and tournament notifications use ID, name, avatar, rank, or player lookup.
- ApiService: Unscoped challenge/ladder-match creation/resolution calls getPlayerById/global mockDatabase.players; stored ladder state is topped up from createPlayers; tournament/gallery seed data uses playerSeeds names/IDs.

B. Screens that break if playerSeeds, createPlayers(), and /players mock response disappear today

In DEMO mode, every direct loader above loses its required player result and will show error/empty UI or lose identity, opponent, participant-name, rank, and action data. DefaultLayout will repeatedly fail its automatic load. The highest impact is /dashboard, /rankings, /challenges, /create-challenge, /play, /play/:matchId, /matches/:matchId, /profile, live-operation routes, and tournament creation/detail routes. Club-scoped LadderView reduces the damage by deriving a roster from club records/entries, but it still loads the global store and uses currentPlayer/currentPlayerId fallback. EMPTY mode intentionally returns [] today; it is not a removal-ready replacement because callers and mock branches still remain.

C. Target ownership of information

- Club member: club-scoped profile (name, photo, contact), membership state, club role/permissions, userId link, provenance, and ladder-membership links.
- Ladder entry: ladderId, active/withdrawn status, position/rank, ordering, eligibility, and competition-specific facts.
- Authenticated account: immutable principal/user ID, sign-in email, preferred account name/avatar, session, and global authorization. It claims/selects a linked member; it is not a synthetic player fallback.
Evidence: memberData normalizes userId/ladderMemberships; AdminService enforces membership; competitionScope.ladderRosterFromSetup maps active entries and positions.

D. Required migration before delete candidacy

1. Establish stable backend account, club-member, and ladder-entry IDs; link accounts to members.
2. Provide scoped current-actor, active-club, member-directory, and ladder-roster/entry APIs; replace every PlayerService GET /players consumer.
3. Use auth for actor identity, club member for profile, ladder entry for rank/eligibility; remove APP_CURRENT_PLAYER and global player fallbacks.
4. Migrate unscoped challenge/match operations, participant lookup, and gallery uploader labels from ApiService.
5. Move player/tournament fixtures and scenario IDs to test fixtures or an explicit non-production seed pipeline; decide local-browser-data retirement/migration.
6. Move source-level legacy tests to behavior tests of canonical routes.
7. Verify EMPTY, DEMO, club-scoped, no-club, challenge, live, and tournament flows. Only then remove playerSeeds, createPlayers, /players, top-up logic, and finally the old player system in an approved change.

Conclusion: old global player data cannot be deleted now.
